# ACDRL-SYS-001 — Spacecraft System Modeling Research Protocol

**Version:** 0.1  
**Status:** Draft for review; not executed.  
**Domain:** Spacecraft and ground-segment cyber-resilience (isolated software simulation).

## 1. Research question
Can a simplified spacecraft–ground-station simulation support reproducible differentiation of normal operations, benign faults, and cybersecurity-relevant anomalies while enforcing defined command-integrity and mission-safety constraints?

This is an **environment-validity and measurement** study, not yet a claim that AI detection is superior or that autonomous defense is safe.

## 2. Objectives
1. Specify the system boundary, message semantics, state transitions, and safety invariants.
2. Implement deterministic, testable normal operations and controlled scenario injection.
3. Verify that labels are generated independently of detector-visible features.
4. Establish rule-based and simple statistical detection baselines.
5. Measure observability, false alarms, missed anomalies, delay, availability, and integrity.
6. Document simulator limitations and reproducibility evidence.

## 3. Testable hypotheses (provisional)
- **H1 — Functional integrity:** In the modeled scenarios, unauthorized or stale commands produce zero unauthorized spacecraft state changes.
- **H2 — Reproducibility:** Identical simulator version, configuration and seed yield identical structured outputs within the declared execution environment.
- **H3 — Measurability:** Scenario outcomes can be evaluated with predeclared metrics and separated ground-truth labels, including cases where benign faults resemble attacks.

H1–H3 are engineering validation hypotheses. Any claim of scientific novelty requires a separate literature-supported gap analysis and empirical findings.

## 4. Independent and dependent variables
**Independent:** scenario class, injected event timing, link latency/loss, command authorization status, queue load, sensor noise, random seed.

**Dependent:** unauthorized state changes, false-positive and false-negative rates, precision/recall where meaningful, detection latency, contact/mission availability proxies, dropped authorized commands, and safety-invariant violations.

## 5. Proposed experimental design
1. Freeze the model specification and scenario catalog before evaluating detectors.
2. Run normal-operation simulations across predefined random seeds.
3. Introduce benign faults at specified times/intensities.
4. Introduce bounded synthetic adversarial scenarios through controlled injection hooks.
5. Validate command authorization and safety invariants using automated tests.
6. Evaluate transparent rule-based and statistical baselines first.
7. Repeat across seeds and summarize uncertainty (e.g., confidence intervals when justified).
8. Preserve negative results, failures, and limitations.

No sample sizes, performance thresholds, or significance claims are asserted before a justified experiment plan exists.

## 6. Data management and leakage prevention
- Generate synthetic data only; no confidential mission or financial records.
- Store simulator configuration, code revision, scenario metadata, dependency versions and seeds.
- Separate scenario labels and injection metadata from detector inputs.
- Define training/validation/test partitions by independent simulation runs where learning is introduced.
- Avoid committing large raw data and secrets; publish small, reviewed example artifacts where appropriate.

## 7. Baselines and metrics
**Baselines:** authorization/freshness rule checks, threshold-based telemetry anomaly flags, and simple rolling-statistics detectors. Baseline definitions must be fixed before comparisons.

**Metrics:** confusion matrix and class-wise precision/recall, false-alarm rate per operating time, detection delay distribution, mission-availability proxy, rejected/accepted command counts, safety-invariant violation count, and computational overhead.

For rare events, accuracy alone is insufficient. Report denominators, prevalence, uncertainty, and failure cases.

## 8. Reproducibility and evidence checklist
Each executed run will produce:
- Experiment ID, timestamp, protocol version, code commit SHA.
- Configuration file, environment/dependency lock or version manifest.
- Random seeds, synthetic dataset/scenario provenance, integrity hashes.
- Machine-readable events, detector outputs, metrics and test results.
- Figures or tables generated by reproducible scripts.
- An explicit limitations and safety note.

Evidence must be indexed in `EXPERIMENT_REGISTRY.md` and `EVIDENCE_REGISTER.md` after execution.

## 9. Acceptance criteria for this protocol stage
- Architecture and trust boundaries reviewed.
- Scenario taxonomy and safety invariants approved.
- State and message schemas specified.
- Baseline definitions and measurement procedures reviewed.
- Literature review initiated and references recorded.
- Only then authorize simulator implementation as a separate milestone.

## 10. Research ethics and safety
Use only local, authorized simulation. No real spacecraft uplink, satellite targeting, ground-station probing, or operational payment-system activity. A detection alert does not authorize disruptive mitigation.

## 11. Expected outputs
A reviewed simulator specification, threat model, test plan, and subsequent reproducible baseline experiment. **No scientific results exist at the time of this protocol draft.**
